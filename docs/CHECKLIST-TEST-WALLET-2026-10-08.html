✅ CHECKLIST — TEST RÉEL AVEC WALLET CONNECTÉ

Rédigé le 08/10/2026 · app buildpact-75mv · Solana Devnet uniquement À dérouler quand un wallet réel est sous la main. Aucun agent n'a exécuté ces parcours : ils signent des transactions, et un navigateur d'automatisation ne peut ni autoriser MWA ni approuver une signature. Cette checklist est donc le seul moyen de valider la partie qui compte.

Deux wallets, dans l'idéal (A = créateur, B = membre). Un seul suffit pour créer, mais l'ajout de membre et l'approbation ne se testent vraiment qu'à deux.

À chaque étape, noter : l'adresse du wallet, la signature de transaction (base58), et une capture. Une signature sans capture ne se rejoue pas.

1. Connexion et identité de l'app (MWA)

  1. Ouvrir l'app sans wallet connecté → le shell premium doit s'afficher (pas d'écran vide, pas de page sombre legacy).
  2. Connecter le wallet A.
  • [ ] La demande d'autorisation affiche BuildPact avec l'URL réelle de la page (window.location.origin).
  • [ ] Refuser une première fois → l'app reste utilisable, pas de boucle de reconnexion.
  • [ ] Accepter → l'adresse apparaît dans la barre de navigation.
  1. Actualiser la page.
  • [ ] La reconnexion est automatique et ne redemande pas d'autorisation.
  • [ ] Déconnecter puis reconnecter → toujours pas de double demande.

⚠️ Point suspect à confirmer ici : la console affiche Phantom was registered as a Standard Wallet. The Wallet Adapter for Phantom can be removed from your app. — l'app enregistre nous-mêmes PhantomWalletAdapter alors que Phantom s'auto-enregistre. Sans effet visible constaté jusqu'ici, mais c'est la première chose que ce test doit trancher : la connexion Phantom fonctionne-t-elle, et une seule entrée s'affiche-t-elle dans la modale ?

  • [ ] Un seul « Phantom » dans la modale de sélection (pas de doublon)
  • [ ] Connexion Phantom réussie, signature demandée une seule fois

2bis. Enregistrement du profil depuis le shell premium

Le 08/10, l'enregistrement du profil premium écrit désormais côté serveur (avant, il n'écrivait que dans le navigateur). C'est le seul correctif de la journée dont la preuve demande un wallet : les tests unitaires couvrent la fusion des champs, pas la signature.

  1. Ouvrir #/profile, cliquer Modifier, changer le pseudo (et si possible l'avatar ou la bannière), puis enregistrer.
  2. Approuver la signature demandée par le wallet.
  • [ ] Le message proposé à la signature est le message canonique de BuildPact (Wallet: … + Timestamp: …) — et non l'ancien texte « BuildPact — Mise à jour du profil : … »
  • [ ] L'app affiche « Profil enregistré — il apparaît maintenant dans l'annuaire des builders »
  • [ ] #/builders : le nouveau pseudo/avatar/bannière apparaît (recharger la page, pour être sûr que ce n'est pas le cache)
  • [ ] Depuis un autre appareil ou navigateur, se connecter avec le même wallet → le changement est là : c'est ce que « distant » veut dire
  • [ ] La bio, les liens, la disponibilité et la palette de thème du profil sont intacts : le formulaire premium ne les expose pas, l'enregistrement ne doit pas les effacer au passage
  • [ ] Refuser la signature une fois : aucun succès n'est affiché, et l'annuaire ne change pas (pas de succès mensonger)

3. Signature des autres chemins (le vrai risque)

Un test « création OK » ne prouve pas les autres instructions. Dérouler ces quatre-là, chacune produisant sa propre signature :

  1. Financer (fund) avec le wallet A — [ ] montant débité, trésorerie du pact créditée, Explorer montre l'instruction fund
  2. Approbation (approve) — [ ] avec B après que A a finalisé ; l'état du membre passe de « en attente » à « approuvé »
  3. Retirer un membre (remove_member) — [ ] tant que le membre est en attente ; refusé si le membre est déjà approuvé
  4. Distribuer (distribute) — [ ] réservé au créateur ; les parts sont réellement transférées (vérifier les soldes avant / après, pas seulement le message de succès)
  • [ ] Aucune transaction « fantôme » : chaque clic qui prétend écrire on-chain produit bien une signature dans la console du wallet
  • [ ] Une signature refusée dans le wallet n'écrit rien et affiche un message dans l'app (pas de succès mensonger)

4. Correction de la description on-chain (les deux pacts pollués)

Deux pacts de démonstration ont un champ description qui commence littéralement par [🤝 Les deux] — c'est le texte stocké on-chain, pas un défaut d'affichage. Le créateur peut le corriger.

  1. Ouvrir la fiche du pact concerné.
  2. Ouvrir EditDescriptionModal (bouton de correction de description).
  3. Saisir une description propre → signer.
  • [ ] Une signature est demandée (update_description)
  • [ ] Reconnexion / actualisation : la nouvelle description s'affiche
  • [ ] Explorer : l'instruction update_description est bien présente
  • [ ] L'ancien texte n'apparaît plus nulle part (carte, fiche, annuaire)

⚠️ Corriger ces deux-là écrit sur devnet : le contenu actuel est perdu. Le noter avant (copier le texte) si on veut le garder quelque part.

7. Ce que cette checklist ne couvre pas

  • Abonnement push réel : impossible depuis un navigateur d'automatisation (Notification.permission y vaut denied). Il manque en plus la paire de clés VAPID. À tester dans un vrai navigateur, une fois les secrets posés.
  • Mainnet : hors périmètre, l'app est devnet.
