Comparaison chiffrée avec concurrents — « non documentée · à valider »

Aucun concurrent direct trouvé qui combine exactement ce que fait BuildPact : découverte de projet + accord multi-partie on-chain + escrow + distribution automatique, natif Solana. Les trois protocoles les plus proches par fonction visent tous autre chose :

  • Sablier — streaming de tokens seconde par seconde, supporte Solana + 24 chaînes. Pas de notion de rôles/parts négociées ni d'approbation multi-partie.
  • 0xSplits — répartition de revenus on-chain, zéro frais, mais 100% EVM (13+ chaînes) ; le support Solana se limite à du bridging d'actifs, pas un déploiement natif.
  • Juicebox — trésorerie programmable et levée de fonds, Ethereum/Arbitrum/Base/Optimism uniquement.

La différenciation du doc ("ni workspace ni marketplace, relie découverte + accord + paiement") tient : personne d'identifié ne fait cette combinaison précise sur Solana.

Sources : 0xSplits docs, Sablier via Gitcoin, Juicebox

Erreur à corriger

« project_id ≤ 32 caractères » — répété dans ce doc et dans le Cerveau Projet

Ton vrai lib.rs a MAX_PROJECT_ID_LEN = 20, pas 32. Les deux chiffres ne se contredisent pas techniquement (32 octets = la limite Solana sur un seed de PDA ; 20 caractères = ta propre limite applicative, plus stricte, imposée par toi dans le code). Mais si quelqu'un — toi, un coéquipier, un juge qui teste — lit "32" dans la doc et crée un projet avec un project_id de 25 caractères, le programme va le rejeter, sans que cette limite de 20 soit écrite nulle part dans les docs produit. Je recommande de corriger le chiffre dans le Cerveau Projet et ce doc, et de tester une fois avec un id à la limite (19, 20, 21 caractères) pour confirmer le comportement exact avant la démo.
