1. Ce qu'est l'app aujourd'hui

Un pacte on-chain entre builders : un projet est publié avec ses rôles et ses parts, d'autres devs postulent, l'accord est écrit on-chain, les backers financent un escrow, la distribution suit.

2. Architecture technique réelle

  • Front : Vite + React 19 + TypeScript + Tailwind. Entrée src/main.tsx, routage par hash (src/lib/router.ts), une route = une page.
  • Wallet : @solana/wallet-adapter avec trois adaptateurs — SolanaMobileWalletAdapter (Seed Vault / Seeker), Phantom, Solflare. Le appIdentity.uri est dérivé de window.location.origin : une identité figée sur une URL Vercel périmée casserait l'autorisation MWA (corrigé).
  • On-chain : programme Anchor create_project, add_member, remove_member, approve, finalize, fund, distribute, close_project, update_description. Aucun compte administrateur modifiable : frais et portefeuille protocole sont des constantes compilées.
  • Hors-chaîne : Supabase (profils, médias, discussion, coffre-fort de documents, annuaire, traductions) + fonctions Edge (push, contact, network-write, quest-write, update-profile, translate, vault, project-write, chat-moderate, open-roles). Règle tenue : aucune écriture publique non vérifiée — les écritures sensibles passent par une signature de portefeuille.

Le comment de ces changements — numérotation des chantiers, commits, mécanismes internes — vit dans PLAN-CHANTIERS-PREMIUM-2026-10-08.md. Ce document-ci dit ce qui a changé, pas comment : un hash de commit ou le nom d'une classe CSS ne veut rien dire pour un lecteur qui n'est pas dans le dépôt.

Le profil premium écrit désormais au serveur. C'est la correction la plus importante de la journée, et elle n'a pas l'air d'un bug : le formulaire premium demandait une signature de wallet… puis écrivait uniquement dans le navigateur. Un pseudo ou un avatar changé côté premium n'apparaissait donc ni dans l'annuaire des builders, ni sur un autre appareil — seul le portail historique écrivait vraiment. La signature demandée ne servait à rien après coup : elle portait un message que le serveur ne vérifiait pas. Désormais l'enregistrement écrit d'abord en local (la fiche se met à jour tout de suite et reste lisible hors-ligne), puis envoie le profil complet à l'Edge Function update-profile avec le message canonique qu'elle sait vérifier. Le profil distant est relu avant l'envoi, pour qu'un champ absent du formulaire premium (bio, liens, disponibilité, palette de thème) ne soit pas effacé au passage.

Deux corrections hors de ces changements, le 08/10. Le sélecteur de décor de fond proposait trois variantes « HD » dont les images n'ont jamais été committées : trois 404 en console à chaque ouverture des réglages, et des vignettes vides. Les trois options sont retirées ; une valeur déjà stockée retombe proprement sur le défaut, et un test refuse désormais toute référence à un fichier absent de public/. Par ailleurs, une bannière carrée débordait de sa vignette et masquait titre, description et chiffres, tandis que le dégradé de repli était écrit en dur à trois endroits, donc hors thème : les deux sont corrigés, avec un test qui balaie toutes les pages premium.

Une seule version vivante par famille. Les doublons qui traînaient à la racine de docs/ — sept feuilles de route, deux dossiers juges, un dossier de présentation en double — ont été déplacés dans docs/archive/ le 08/10/2026 : rien n'a été effacé, mais il n'existe plus qu'une feuille de route par langue (ROADMAP-FR.md, ROADMAP-ENG.md) et un seul dossier juges par langue (JUDGES-FR.md, JUDGES-ENG.md). Pourquoi ceux-là : les variantes JUDGES FR.md / JUDGES ENG.md, arrivées le 08/10 avec l'import du dossier de travail, étaient un instantané antérieur — elles n'ont pas la passe d'audit du 19–20/09 que portent les versions à trait d'union.

Où ils vivent. Tous ces documents sont dans le dossier docs/ du dépôt de l'app (buildpact-75mv/) — il n'y a plus qu'un seul dépôt. Les fichiers .html, les scripts de contrôle et les documents d'archive ont été rapatriés du dossier de travail qui les contenait : deux dépôts pour un seul projet, dont un qui ne pouvait pas être poussé, était une source de divergence permanente.

Pourquoi deux documents de référence (FR et EN) et pas un seul

Parce que les textes anglais du hackathon étaient une fusion automatique ligne à ligne (français puis anglais collés), parfois faux (« damage » pour « casse »). Les versions EN d'aujourd'hui sont rédigées, pas générées. Les .html sont produits depuis les .md par docs/outils/md-to-html.mjs : une seule source par langue, donc pas de divergence possible entre le Markdown et le HTML.

Vérifier que les documents n'ont pas divergé

Depuis la racine de l'app (buildpact-75mv/) :

node docs/outils/verifier-docs.mjs   # échoue si un .html ne correspond plus à son .md

Le contrôle régénère chaque page en mémoire et la compare octet à octet à celle du disque : il attrape le .md modifié sans régénération comme le .html retouché à la main. Seules les pages qui portent la signature du générateur sont comparées — les roadmaps d'août existent en .md et en .html sans que l'un dérive de l'autre, les inclure produirait deux fausses alertes.
